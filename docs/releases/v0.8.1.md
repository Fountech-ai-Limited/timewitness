# v0.8.1

A stamp could write a receipt its own `verify` refused. This release stops that.

**What was wrong.** A stamp takes its reading, then gathers the outside evidence. Up to `v0.8` it
asked a Roughtime server for a corridor first, then asked drand for its newest round, and kept that
round if it was dated within two minutes either side of the reading. When anything between the
reading and that fetch was slow, the newest round could be one published after the latest moment
the receipt claims. A round of three seconds is enough for that, and one server timing out is five.
The receipt then said the moment was no earlier than a time after its own interval, which is a
receipt contradicting itself, and `verify` refused it. On 2026-10-08 the released `v0.8` Linux
binary did this: it stamped, exited 0, and its own `verify` refused the receipt because the
round was 2.204 s past the receipt's latest moment.

The corridor had the same fault. It is asked after the reading too, and when the first server timed
out, the next one could answer for a moment wholly after the receipt's interval. A corridor is
evidence for a reading only where the two overlap.

Every release from `v0` carries the same order. Through the Action the damage stopped short of a
workflow's outputs: the Action runs `verify` straight after the stamp and fails the step when it
refuses, so no Action run handed such a receipt on. The command line on its own wrote it and exited
0. Any such receipt is refused by every verifier, the command line and the page at
`timewitness.dev/verify` alike, and that refusal is right. A receipt `v0.8.1` writes is checked by
the same verifier and nothing about how a receipt is read has changed.

**What changed.**

- The drand round is fetched before the reading. A round nobody could know before it was published,
  fetched first, was published first, so it sits under the moment the receipt is about. It is kept
  unless it is more than two minutes behind the reading. The round is not chosen from the reading,
  because a round picked off our own interval would always agree with it, and that would be our own
  bound presented as somebody else's evidence.
- A corridor that answers for a moment wholly after the receipt's interval is set aside, the run
  says why in a line of its own, and the next server is asked.
- Before the receipt is written, it is read the way `timewitness verify` reads it with no options:
  the same checks, the same published keys, the same floor. Where that refuses, nothing is written,
  the stamp exits 1 and says which check refused. A witness over the signature that verify refuses
  is left off rather than costing the receipt, because it sits outside the signature and nothing in
  the receipt rests on it.

A round fetched before the reading is up to a few seconds behind it, as one fetched after was up to a
few seconds ahead. How the interval is worked out has not changed, but when the clock is read has. A
one-shot stamp now waits for the round before it reads, so when every drand relay is slow to answer
it reads its clock that much later, and the interval it states is wider by what the clock model
allows for the wait. A stamp that reads from a running agent with `--agent` is not widened by the
wait, because the agent keeps its model current while the stamp waits.

The tests stand in for every party outside the machine on a clock of their own, with real drand
rounds, a real corridor and a real token, and read every receipt with the verifier that ships.
Three of the five written first fail on the order `v0.8` used.

Signed binaries for Linux, on x86_64 and aarch64, are attached, as they were to `v0.8`. Check them
with `python scripts/the-binaries-are-signed.py --release v0.8.1 --linux-only`. No macOS or Windows
binary is released, because neither can be signed yet, so on those systems the command line is built
from source.

What TimeWitness cannot prove is in `docs/what-timewitness-cannot-prove.md` at this tag, and it
binds every sentence above.
