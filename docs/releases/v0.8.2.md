# v0.8.2

A stamp could write a receipt over a reading its own corridor contradicted, by setting that corridor
aside as late. This release stops that.

**What was wrong.** `v0.8.1` fetches the drand round before the reading, then asks a Roughtime server
for a corridor after it. A corridor asked after the reading is about a later moment, and when the
first server times out the next one can answer for a moment wholly after the receipt's interval. So
`v0.8.1` set aside any corridor that started after the latest moment the receipt claimed, as an
answer too late to speak to the reading, and asked the next server.

It never asked how long after the reading the corridor answered. A reading slow by more than its own
bound puts every honest corridor after the receipt's interval, however promptly the server answers,
so every corridor was set aside as late and the receipt was written with none. It verified, and
`verify` said, correctly, that the width was the signer's own claim and that the receipt carried no
corridor. In a test with a reading 1.5 s behind the moment it was taken, a bound of 186 ms and a
corridor that answered in 50 ms, `v0.8.1` wrote the receipt. `v0.8` kept that corridor and its
`verify` refused the receipt, which was the answer to give.

The beacon does not catch this on its own. A round is published every three seconds, so a reading
can be wrong by a second or more and still be later than the round fetched before it.

**What changed.**

- A stamp reads this machine's monotonic counter when the reading comes back, and again when each
  corridor answers. A corridor wholly after the receipt's interval is set aside only where that wait
  explains it: its midpoint is past the latest moment the receipt claims by no more than the wait and
  the corridor's own radius. An honest server asked at the moment of the reading could not be further
  out than its radius, and the wait can move it on by no more than the wait.
- Any other corridor is kept. One further after the interval than the wait explains is kept, and so
  is one wholly before it. The check before the file, which `v0.8.1` added, then refuses the receipt,
  nothing is written, and the stamp exits 1 and says which check refused.
- A corridor that really is late, because the server before it took five seconds to time out, is
  still set aside, the run still says why in a line of its own, and that line now says how long after
  the reading the corridor answered.

The wait is read after the reading is in hand, never before it is asked for, so it is never counted
as longer than it was. Counted short, a corridor that was late can be kept and the stamp refused,
which costs a stamp and never a wrong receipt.

What `v0.8.1` fixed still holds: the round is fetched before the reading and never chosen from it,
and a stamp never writes a receipt its own `verify` refuses. How a width is worked out, the receipt
format and how a receipt is read are all unchanged.

A receipt `v0.8.1` wrote over a reading its corridor contradicted carries no corridor and says so,
so nothing in it claims what it does not have. The interval in it is our own claim, and that is all
it ever said it was.

The tests stand in for every party outside the machine on a clock of their own, with real drand
rounds, a real corridor and a real token, and read every receipt with the verifier that ships. The
one for a slow reading against a prompt corridor fails on `v0.8.1`.

Signed binaries for Linux, on x86_64 and aarch64, are attached, as they were to `v0.8.1`. Check them
with `python scripts/the-binaries-are-signed.py --release v0.8.2 --linux-only`. No macOS or Windows
binary is released, because neither can be signed yet, so on those systems the command line is built
from source.

What TimeWitness cannot prove is in `docs/what-timewitness-cannot-prove.md` at this tag, and it
binds every sentence above.
